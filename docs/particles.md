# Native particle foundation — EAF-212

## Contract before implementation

Guilherme authorized particle work after the shared material foundation203 and
explicitly deferred mirrors. The first increment is a native, reusable effect
source with emitters and separate placements, rather than effect-specific meshes.
This is the first stage of [the VFX requirements](particle-vfx-requirements.md).

Sources define rate/burst emission, seeded shape/cone sampling, lifetime, color,
size, rotation, material and a typed module stack. Initial modules cover constant
acceleration, linear drag, kinematic waves and color/size curves over lifetime.
Acceleration and drag coefficients add across modules; waves apply kinematic
displacement after the base trajectory, and life curves multiply birth values.
The CPU evaluates trajectories analytically at a fixed60Hz timeline. This is a
bounded, stateless reconstruction backend, not a general integrated particle/fluid
solver. Camera movement does not reseed or advance the effect. Births have stable
source/placement/emitter/kind/ordinal identities; random channels are independent.

World simulation time is the default clock. An explicit session preview tick can
freeze/seek the effect without advancing physics; clearing it resumes world time.
Scene/save/replay preserve sources/placements and reconstruct cosmetic state from
the saved world tick. Preview clock is editor/session state, not gameplay state.
Looping sources emit continuously and repeat bursts at the source period; finite
sources stop emission and drain living particles. Disabled instances kill their
presentation. Source edits use the normal atomic authoring/reset/history contract.

Billboards are generated by a six-vertex GPU draw from an80B instance stream:
position/size, velocity/angle, color/alpha, shape and material slot. No authored
mesh, actor or material is created per particle. The renderer uses the shared
material/shading and colored-transmission OIT passes, with per-particle tint and
coverage. Circular soft profiles, aspect ratio and velocity alignment are generic
sprite controls. These are lit/translucent sprites, not volumetric smoke.

Positions are authored with canonical global Position1 addresses; the initial
ordinary-scene adapter projects to the existing metre frame. Unrepresentable
particles are omitted with diagnostics. Planetary rendering has an explicit
unsupported boundary in this increment; it must never retain stale particle
buffers or reinterpret global positions in the planet's normalized frame.
Physics, damage, attachment identities, collision, soft intersections, event
subemission, ribbons, simulation GPU, arbitrary graphs and fluid solvers remain
later contracts. Public visual content may carry only cosmetic effect definitions;
particles never become an authoritative gameplay or private NPC data source.

## Static performance review

- Validate/compile source/module coefficients once per immutable document;
  evaluate only the recent birth window, not all elapsed history.
- Bound source bytes, modules/curves, live population and candidate work. Budget
  drops/expired/projection failures are inspectable and cannot change gameplay.
  Admission order is deterministic, not a claim of unlimited density or fairness.
- Retain frame/sample/upload buffers. Same document/time reuses evaluated data;
  camera-only changes use GPU uniforms without CPU trajectory work or uploads.
- Material storage scales with emitters/placements as needed, never particle
  count. Reuse shared material programs and GPU resource limits.
- No particle triangles are expanded/copied on CPU; no readback, extra thread,
  lock, file read or bake occurs in frame drawing. Source file IO is explicit.
- Empty particle documents retain the existing path and allocate no particle/OIT
  targets. OIT/overdraw remain real costs; no FPS or cross-platform determinism
  claim follows from headless correctness.

## Validation gates

Independent rate/burst and trajectory oracles; seed/order/seek stability; curve
endpoints, lifetime drain and bounded overflow; invalid edits and format gates;
native GPU depth/tint/alpha and camera-facing geometry; warm/cold frame reuse;
scene/replay/portable-save reconstruction; explicit planetary/network policy.
Editable spark and smoke examples are reviewed through native captures, with
artistic acceptance and physical editor interaction kept separate.

## Authoring and formats

`Particles` (`command.op = "particles"`) exposes `inspect`, `preset`, `replace`,
`put_source`, `remove_source`, `put_instance`, `remove_instance`, `preview`, `open`,
`save_source` and `load_source`. Mutation uses the normal revision/undo transaction;
source removal refuses live references. `preset` creates a source plus a placement
and requires a new ID. File operations are confined to the selected project root,
limited to 8 MiB and use the `.ignis-vfx` suffix and atomic replacement.

```json
{"command":{"op":"particles","operation":{"kind":"preset","preset":"sparks","id":"fire"}}}
{"command":{"op":"particles","operation":{"kind":"preview","tick":90}}}
{"command":{"op":"particles","operation":{"kind":"inspect"}}}
{"command":{"op":"particles","operation":{"kind":"preview","tick":null}}}
```

The **Partículas** panel offers presets, preview time and source load/save. Its
editable JSON document exposes the complete typed schema (including material and
module parameters); applying validates the candidate before publication, while
Discard restores the current document. This is initial authoring, not a visual
node graph or curve editor. Ordinary Play/Pause controls the world clock.

Effect/source1 requires Scene113 or newer. Build-scoped replay and public visual
content use their current versioned readers and reject incompatible packages.
PSV1/checkpoint3 containers retain their
own contracts and require their current embedded scene schema. Authoring scene
files store descriptors, not live particle arrays or the preview clock. Clients
receive only cosmetic source/placement definitions and reconstruct at replica
time. Remote authoring/preview is refused, rather than changing local content
that would not affect the received world. No per-particle traffic is emitted.

## Limits and admission

Default world budget is 8,192 live sprites (authorable 1..262,144), with up to
128 sources, 256 placements, 32 emitters/source and 16 modules/emitter. Curves use
2..16 ordered keys with endpoints 0 and 1. An emitter budget is 1..65,536.
A conservative product of birth size, aspect and maximum size-curve values
cannot exceed 1,000 km before placement scale; this also prevents numeric
overflow from stacking large curve multipliers. Lifetimes are 1..3,600 ticks; source periods are 1..36,000 ticks. Rate is quantized
to milliparticles/second (minimum nonzero 0.001; maximum 100,000). Birth `k>=1`
occurs at `ceil(k*60000/rate_milli)` ticks after emitter delay; burst includes tick
zero. A finite source stops rate births before its duration and emits one burst.
Looping rate remains continuous; bursts repeat every source period.

Only the recent maximum-lifetime birth window is examined. Candidate work is
bounded by 16 times the world budget and 16 times each emitter budget. Source and
placement order determine admission under overload; rate candidates are admitted
before burst candidates within that work window, then sorted by newest birth.
This intentionally makes no fairness or density guarantee. Diagnostics distinguish
candidates, trajectories evaluated, expired samples, admission drops, projection
drops and work-limit truncation; drops are not an exact census of unexamined
births. All scratch, frame, coefficient and GPU instance buffers are retained.

Position1 projection uses the zero metre-frame origin, a 1,000 km radius and
1 mm maximum per-axis conversion error. Samples outside those limits are omitted.
The planetary path clears particle frames; enabling it with authored placements
refuses explicitly. The renderer also rejects sprites with reverse-Z/planet air
frames. No planetary behavior is implied by global addresses.

Particles share opaque depth testing and colored-transmission OIT. They do not
write depth, cast shadows or collide. Sprite rest coordinates are `(u,v,0)`;
planar procedural recipes should select their XY domain. Material storage scales with placed
emitters, including stable per-placement procedural material variation when the
shared recipe requests it. Empty effects allocate no sprite buffer or OIT target;
a previously used sprite allocation remains reusable. There is currently no
per-particle frustum/occlusion compaction; transparent overdraw remains a cost.

## Validation evidence

Formatting and all-target release Clippy passed for the isolated particle change
set on the public repository base. The shared development checkout contains
independent work in progress, excluded from that isolated check.

`cargo test --locked --release --test particles --test material_transparency
--test network_content -- --include-ignored --test-threads=1` passed all 15 tests.
The particle tests include independent motion/schedule oracles, fixed-time/seek
and seed-channel stability, bounded overflow at `u64::MAX`, projection and curve
behavior, atomic rejection/undo, source IO, scene/replay/portable reconstruction,
public content and explicit planetary refusal. Native GPU checks assert numeric
additive and blended tint/alpha, opaque depth, camera-facing sprites and no
upload/evaluation on camera-only updates. A regression guards material slot zero
for legacy boxes in scenes without mesh assets.

`python3 scripts/demo_particles.py` passed eight MCP groups and regenerates the
editable [scene](../examples/particles.scene.json), [sparks](../assets/particles/sparks.ignis-vfx)
and [smoke](../assets/particles/smoke.ignis-vfx) sources. Local outputs are
`artifacts/particles/review.html` and `verification.json`. Same-time, seek-return
and portable-restore native PNGs match exactly. The native editor panel renders;
this does not establish human mouse/keyboard acceptance or artistic approval.

On Apple M4 Pro / Metal, the 1280×800 gallery has 40, 106, 131, 155 and 208 live
sprites at ticks 0, 45, 90, 150 and 240. Tick150 uses one sprite draw, 12,400 active
instance bytes and 20,480 allocated instance bytes; warm same-time captures retain
the upload count. Shared OIT targets use 28,672,000 logical bytes at that resolution.
These are this small workload's counts, not a sustainable capacity or FPS claim.
The user's running scene/window is preserved; validation uses isolated captures.

## Parametric fire

[Fire families](particle-fire.md) add candle, campfire, torch, blue jet, inferno and
arcane sources with intensity, nominal height/width, turbulence and seed controls.
Use the fire section of the Partículas panel, or the same typed operation:

```json
{"command":{"op":"particles","operation":{"kind":"fire","id":"campfire","settings":{"kind":"campfire","intensity":1.4,"height":2.0,"width":1.2,"turbulence":0.7,"seed":7}}}}
```

Source2 stores the compact recipe and regenerates immutable emission/opacity maps
at admission. Source1 remains supported. `detach_fire` preserves the generated
emitters for explicit manual editing; regeneration then refuses to overwrite them.
This uses the existing material/sprite backend; no new rendering pass is added.
The editor's Apply and run action pauses, publishes the edit and resumes world
time, clearing any fixed particle preview. The ordinary authoring reset/undo
contract applies. Nominal height/width are scales; the visible envelope also
depends on life, movement, style and intensity.

The editable gallery is [particle-fire.scene.json](../examples/particle-fire.scene.json).
Run `python3 scripts/demo_particle_fire.py --open` to regenerate/verify and open it,
or `--open-only` to open the current gallery. Existing human windows are preserved.
